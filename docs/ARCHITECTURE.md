# Acadia — architecture

How the code is organised. Update this file in the same PR as any
change to module boundaries, the memory map or zero page.

## 1. Layers

```
+---------------------------------------------------------+
| game logic   rules, economy, events, AI, screens        |  platform-independent
+---------------------------------------------------------+
| services     tiles/map, sprites, sound driver, text     |  uses only equates
+---------------------------------------------------------+
| platform     hw_*, mem_*, plat_*, input*, interrupts    |  swapped for 5200
+---------------------------------------------------------+
```

Game logic never touches hardware registers or OS variables directly.

### 3a. Memory map (5200, 32K cartridge, D62)

Set in `src/mem_5200.asm`. RAM is `$0000-$3FFF`; only reserved blocks
(`*= *+n`) are assembled there, as a cartridge loads nothing into RAM.
`make 5200` prints the free bytes (`tools/mkcart.py`).

Variables: all RAM variables live in one block, `src/vars.asm` at
`$3900`, never inline after code, so the same source can run from a
5200 cartridge (AGENTS.md rule 8). Storage is reserved with `*= *+n`
only, so nothing depends on the loader: `VARS_INIT` clears the block
and sets the few non-zero start values (e.g. `KEY` = `$FF`). This
includes RAM screen memory such as the status lines, which are copied
from a constant template at start-up. Add new variables to `vars.asm`,
grouped by module.

5200 budget: the 5200 has only 16K of RAM (`$0000-$3FFF`), with code
and constant data in cartridge ROM. Screen, display list, P/M graphics,
any RAM-resident font and all variables must fit in roughly 14K. Keep
that in mind before growing RAM buffers.

Constraints: fonts 1K aligned (modes 2/4/5); screen memory must not
cross a 4K boundary without a new LMS; display lists must not cross a
1K boundary; P/M base 1K (double-line) or 2K (single-line) aligned.

## 4. Platform interface

Everything the game needs from the machine, so a 5200 build can
provide the same symbols.

**Input** (`input.asm`, call `INPUT_POLL` once per frame):

| Symbol | Meaning |
|---|---|
| `JOY0`, `JOY1` | Direction bits, 1 = pressed: b0 up, b1 down, b2 left, b3 right |
| `FIRE0`, `FIRE1` | 1 = fire held |
| `KEY` | Item key 0-9 pressed this poll (edge), else `$FF` |
| `KEYPL` | Player the key belongs to: 0 or 1 (D17: fire held picks the player; neither → 0); `$FF` if both held, and then `KEY` is `$FF` too |
| `CONKEY` | START/SELECT/OPTION held bits (b0/b1/b2), for the D18 info displays |
| `PAUSEK` | 1 on the poll where the pause key was pressed (P on the 800, PAUSE on a 5200 keypad), D19 |
| `HELPK` | 1 on the poll where H or the XL/XE HELP key was pressed (help screen, D34) |

During a game `GAME_FRAME` also calls `FIRE_TAP` after `INPUT_POLL`: a fire
press let go with no key in between sets `KEY` = 0 and `KEYPL` = that
player on the release (D60). `FTAP` holds each player's state; `GAME_START`
sets it to `FX_USED` so a fire held over from the setup screen does not count.

Keypad controller (D49, D58; CX21 Video Touch Pad or CX50): `KP_ON` / `KP_OFF` switch port 2 between a
stick and a keypad (`KPMODE`). With the keypad on, `JOY1` and `FIRE1`
stay 0, its digits come in as `KEY` with `KEYPL` 0, * as `PAUSEK`
and # as `HELPK`. In a 1-player game `GAME_START` calls `KP_AUTO`,
which turns it on if a keypad is plugged into port 2 (its pulled-up
columns charge pots 2 and 3 at once, D58); `SETUP_ENTER` turns it off.

5200 mapping (`input5200.asm`, D63): each analog stick (the BIOS's pot
shadows `PADDL0-3`, low = left / up) past a dead zone (under 74 or from
155, centre ~114; both pots at 228 = no controller) gives `JOY0` /
`JOY1`. POKEY scans the keypad and the bottom side button (`SKSTAT`
bit 3), which gives `FIRE0` / `FIRE1`, of the one controller
`CONSOL` bits 0-1 select (bit 2 kept set: pots on); `INPUT_POLL` reads
the controller selected the frame before, then selects the next:
controller 1 every frame, the two in turn during the rounds of a
2-player game. Keypad 1-9 → `KEY` with `KEYPL` = the controller; 0 and
the top side button (`TRIG0/1`) → `KEY` 0 on the press; `*` → `HELPK`; `PAUSE` →
`PAUSEK`; `START` held → `CONKEY` bit 0; `#` held during a round →
`CONKEY` bit 0, 1 or 2 (totals, then the next page on each press within
1.5 s of the last). `*`, `#`, `START` and `PAUSE` are shared: a press
counts unless the other controller holds the same key. `KEYDOWN` = any
key or top button held. `FIRE_TAP`, `KP_ON`, `KP_OFF` and `KP_AUTO`
are an `RTS`. `IN_INIT` (from `PLAT_INIT`) turns off the bottom button's
BREAK IRQ, as input is polled.

**Interrupts:** the game installs a deferred VBI (`VVBLKD`) and a DLI
(`VDSLST`) by writing the RAM vectors with `NMIEN = 0`, then
re-enabling NMIs. The deferred VBI chains to the previous handler via
the saved pointer `OLDVBD`. No OS routine is ever called. On the 5200
that previous handler is `PLAT_VBI`, which copies `CHBAS` and `GPRIOR`
(RAM bytes there: the BIOS has no such shadows) to the hardware and
then jumps to the previous deferred vector (D62): `BT_XIT`, the end of
`BT_VBI`, the cartridge's own immediate VBI (D77).

**Start-up and hooks (D62):** each build's `START` does its machine's
set-up and jumps to `MAIN_INIT` (`main.asm`). `PLAT_INIT` runs right
after `VARS_INIT`; `PLAT_MAP` runs in `MAP_LOAD` right after a map's
block is copied over the live tables. On the 800 `PLAT_INIT` hooks
RESET and loads map 1, and `PLAT_MAP` is an `RTS`; on the 5200 they set
up the BIOS-less shadows and load map 1, and copy the live map's fonts
into RAM.

**5200 start-up without the BIOS screen (D77):** the header's `$BFFD`
= `$FF` makes the BIOS jump to `START` right after `SEI`, `CLD` and a
fresh stack, skipping its title screen and all its set-up. `START`
jumps to `BT_INIT` (`boot5200.asm`, code block 2), which clears RAM
(`$0100-$3FFF`), the chips' registers and the zero page, points the
vectors at its own handlers (`BT_IRQ`, `BT_VBI`, `BT_XIT`, `BT_RTI`;
the BIOS's are at different ROM addresses in different BIOS
revisions), sets `CHBASE` and `SKCTL` (keypad scan) and jumps to
`MAIN_INIT`. `BT_VBI` does the BIOS's VBI work: `RTCLOK`, `ATRACT`,
shadows to the hardware (attract colours as the BIOS does them), pots
into `PADDL0-7`, `POTGO`, then `VVBLKD`. No IRQ is enabled.

**RESET (D76):** `RESTART` (`main.asm`) is the start-up again from a
fresh stack, so RESET lands on the title screen as at power-on. On the
800 RESET is the OS's warm start, which keeps RAM, clears its own
($0010-$007F, $0200-$03FF), sets the hardware up and calls `DOSINI`:
`PLAT_INIT` points that at `RESTART`, sets `BOOT?` bit 0 and `COLDST`
= 0. On the 5200 RESET is a keypad key: `INPUT5200.ASM` jumps to
`PLAT_RST`, which first restores the BIOS's deferred VBI vector, since
nothing else has reset the machine.

## 5. Frame loop

```
VBI (every frame):   FRAME++, ATRACT=0, sound driver step, sprite positions
Main loop:           wait for FRAME change, then GAME_FRAME:
                     INPUT_POLL
                     setup screen (GS_SETUP): SETUP_FRAME only
                     game over (GS_OVER): OVER_FRAME only
                     HELP_KEY: H / HELP toggles the price list; while
                       it is up skip everything below
                     PAUSE_KEY: P toggles pause; while paused skip
                       everything below except the sprite drawing
                     AI_FRAME (1 player: the CPU's stick and purchase)
                     cursor/boat movement from input, buying (ECO_KEY)
                     if tic due (20 Hz): run TIC tasks
                       news slot timer (NEWS_TIC, in GAME_TIC)
                       fish (FISH_TIC), weather (WTH_TIC) and pirates
                       and boat collisions (PIR_TIC), the CPU (AI_TIC),
                       rounds only
                     FISH_SHOW: draw the schools in P3, fill HP3ROW
                     WTH_SHOW: draw the weather in P2, fill HP2ROW, WCROW
                     PIR_SHOW: draw the pirates in the missiles, fill HMROW
                       once per second: clock
                       end of round: economy, population, score, rebels
                     redraw changed tiles / status fields
```

Rule: anything that writes screen memory or colour registers mid-frame
must be safe against the DLI (only the DLI writes hardware colours; game
code writes RAM copies). The map palette is such a copy: `MAPPAL`, set
by `PAL_NORM` (D16 colours) or `PAL_DIM` (half brightness, pause).

## 6. CPU budget

NTSC frame ≈ 29,800 cycles; with mode 4 + mode 2 DMA and P/M DMA,
assume ~18,000 usable per frame. Targets:

- VBI (sound + sprites): ≤ 2,500 cycles
- Per-tic logic: ≤ 8,000 cycles
- AI decision: ≤ 10,000 cycles, spread over frames if needed
- End-of-round scoring may take several frames (the clock is stopped)

## 7. Data model (game state)

Indexed by player `P` = 0 (left island) or 1 (right island). Keep the
original's layout so the formulas port directly:

| Variable | Size | Notes |
|---|---|---|
| `GOLD[P]` | 16-bit | current gold |
| `POP[P]` | 16-bit | population, cap 9999 |
| `SCORE[P]` | 16-bit | total score |
| `RSCORE[P]`, `PRSCORE[P]` | 8-bit | this / previous round score |
| `RGOLD[P]` | 16-bit | gold earned this round (8-bit in original; widened, R-RULE-8) |
| `COUNT` | 8-bit × 20 | items owned: `COUNT`+k for player 1's item k, `COUNT`+10+k for player 2's |
| `MAPITEM` | 8-bit × 220 | item on each square, 0 = none, 1-9 (RAM); kind + owner in `ISLKIND` and terrain in `ISLTILE` (constant), all 20 × 11, index = row × 20 + column |
| timers | 8-bit | `REMSEC`, `TICSEC`, `CURTRN`, `NUMTRN`, `TRNLEN` |
| event counters | 8-bit | fishing, rain-on-crop, weather damage per player |

The logical grid is the original's 20 × 12 cards (each card = one
island square). On screen each square is 2 × 2 mode 4 characters
(D50, was 2 × 1 mode 5, D12); 11 of the 12 rows are visible under the status bar, which is
enough because the islands use about 7-8 rows.

## 8. Naming conventions

- Routines: `MODULE_VERB` (e.g. `MAP_BUILD`, `ECO_INCOME`).
- Internal labels: 2-3 letter module prefix + `_` (e.g. `EC_LOOP`).
- Equates: hardware as in Atari docs; game constants `C_` colours,
  `T_` tiles, `I_` items (1-9 as the original), `MAX_`/`MIN_` limits.

## 9. Map tiles and islands

A map square is one **tile**: 2 × 2 ANTIC mode 4 characters, 8 × 16
pixels shown 8 colour clocks wide and 16 scan lines tall (D50). Colours
(D16, D50): `00` sea (COLBK), `01` grass (PF0), `10` brick red (PF1),
`11` sand (PF2), or white (PF3) in characters with bit 7 set. A
character is 4 × 8 pixels, so one character can't hold both sand and
white; a tile's four characters can each be inverse or not.

Everything is generated by `tools/mkfont.py` (edit it, rerun
`python3 -I tools/mkfont.py`, never edit the outputs;
`--preview build/preview` also writes a PNG preview of the islands):

- `src/tiles.asm`: fixed-tile and cell-kind equates
- `src/font_map.asm`: the map fonts
- `src/islands.asm`: `TILECH`, `TILECTR`, `TILECBL`, `TILECBR`
  (each tile's four character codes), `HLPCH` / `HLPCHR` (help font
  codes), `ROWFONT` (22 character rows), `ISLKIND` and
  `ISLTILE` (220 bytes each, row-major, index = row × 20 + column),
  and the CPU's step tables `AI_HD`, `AI_UP`, `AI_DN` (same layout:
  steps by sea, 4 ways, to player 2's harbour, rows 0-1, rows 9-10;
  `$FF` for land)

**Islands (D23, D24).** Each island is a square outline in the generator
(`.` sea, `#` land, `H` harbour, `r` rock). A seeded, deterministic
erosion pass (value noise at 3 and 6 px scales plus per-pixel jitter,
depth 0-3 px from the sea, mostly 1) makes the coast ragged inside the
land squares, which stay about 85-90 % land. It never adds land to a
sea square, keeps each land square's centre, keeps a 4-pixel band
through squares that join land on opposite sides (no thin necks),
keeps the square behind a harbour whole, and fills enclosed lakes. The
generator also rejects sea squares enclosed by land. Harbours sit one
square in from the screen edge (column 1 / 18) so the pier isn't
clipped by overscan. The
160 × 88 bitmap is then doubled to 160 × 176, smoothed (kept inside
the land squares) and cut into 8 × 16 squares: land pixels next to
the sea are sand, the rest a repeating grass texture (`GRASS`), and
sea pixels next to the land inside a land square are surf; where a
character would hold both sand and surf, the one with more pixels
wins. Every square with any land
is a land square: buildable, and boats can't enter it. The generator
checks the open sea bands and channel and prints per-island numbers
(land squares, full vs coast squares, land pixels and their share of
the land squares, coastline length, harbour position).

**Tiles and fonts.** Fixed tiles come first and have the same
character codes in every font:

| Tile | Equate | Contents |
|---|---|---|
| 0 | `T_SEA` | Open sea |
| 1 | `T_GRASS` | Plain grass (full land square) |
| 2-10 | `T_ITEM` + k − 1 | Items 1-9: fort, factory, crop, school\*, hospital\*, house, rebel, PT boat, fishing boat |
| 11 | `T_WRECK` | Wreck of a parked boat |
| 12 | `T_SPARE` | Spare (blank) |
| 13 | `T_ROCK` | Rock (decorative) |
| 14, 15 | `T_PIER_W`, `T_PIER_E` | Harbour pier, land to the west / east |
| 16, 17 | `T_WAVE1`, `T_WAVE2` | Open sea with wave glints (scattered by the generator) |
| 18+ | — | Coast squares, unique per position (`N_TILES` in all) |

\* white, drawn with inverse characters.

Characters, not tiles, fill the fonts. The fixed tiles' characters,
deduplicated, come first with the same codes in every font; each coast
character goes into the font of the character row it is on.
Consecutive character rows share a font while it fits (128
characters); a new font only starts on an odd character row (D52). `ROWFONT` gives each character row's font page; the
last status line's DLI sets row 0's font and the map colours, and a DLI at the
end of each character row 0-20 sets the next row's font
and its sea and grass colours (`ROWBK`, `ROWPF0`, D51). The DLIs
alternate (D52): `DLI_ROW` starts a square's second character row
(font, shades) and looks up the next square row's `HP2ROW`, `HP3ROW`
and `WCROW` into `DL_NP2`, `DL_NP3` (zero page) and `DL_NC`, and
stores its own font and colours from `DL_NFN`, `DL_NBK`, `DL_NPF`
(zero page, looked up by `DLI_MAP` or `DLI_SQ`) right after `WSYNC`, so
they too take effect on its first scan line (D55); `DLI_SQ`
starts a square row and stores those first, saving only A and X, so
they take effect on the row's first scan line (set any later, the
mode 4 character DMA delays them and cuts off the top of a shape),
then the shades and the missiles; each sets `VDSLST` to the other,
except that after row 20 `DLI_ROW` sets it to `DLI_END`, which at the
end of row 21 makes COLBK the dark corner sea below the map (D67).
The corner rows (0-2, 19-21) are wide playfield lines (D67): `DLI_MAP`
and `DLI_ROW` write `DMACTL` (`ROWDMA` per row, looked up into `DL_NDM`
by the DLI before) as their first store after `WSYNC`, before the
row's DMA starts, and `DLI_END` sets normal width again. A DLI in a
wide line has few free cycles, so `DLI_ROW` does almost nothing before
its `WSYNC`.
Where a square row starts (even character rows) `DLI_MAP` and `DLI_SQ` load `HPOSP3` from
`HP3ROW` (the fish player's position for that row, 0 = off screen),
`HPOSP2` from `HP2ROW` and `COLPM2` from `WCROW` (the weather's),
and `HPOSM3`-`HPOSM0` from `HMROW` (the pirates': M3 at `HMROW`, the
others 2, 4 and 6 colour clocks right of it, so the four missiles
make one 8-pixel fifth player); the deferred VBI parks P2, P3 and the
missiles at 0 for the status bar. The deferred VBI resets
`VDSLST` to `DLI_ST` each frame.

**Status bar** (D54): two ANTIC mode 4 lines in `STFONT`, colours
from the OS shadows (`ST_COLS`: PF0 gold `$2C` for the gold bar and the
heads, PF1 red `$48` for player 1, PF2 white `$0C` for text, PF3
turquoise `$AC` for player 2 through inverse characters; COLBK black
for the blank lines above). A DLI on the last blank line (`DLI_ST`)
sets line 1's background (`$84`) and PF1 (`ST_L1`: the gold bars'
dark gold `$26` while they show, red on the score pages), one on line 1
(`DLI_ST2`) line 2's background (`$80`) and PF1 (red), all with attract
mode applied in `ST_VBI`; then `DLI_MAP`.
`HDLIST` starts the same way. The title screen sets `CHBAS`
to its own font (`TTFONT`, D70), the setup screen to the help font (D65). `TILECH[t]`, `TILECTR[t]`,
`TILECBL[t]` and `TILECBR[t]` are tile `t`'s four character codes
(inverse bit included); `MAP_PUT` writes them, and `MAP_PUTI` ORs
`MPINV` into each (player 2's parked boats, white). Items replace a square's terrain tile on screen;
`ISLTILE` keeps the terrain to restore.

**Cell kinds** (`ISLKIND`): `K_SEA` 0, `K_LAND` 1 (any land: buildable,
blocks boats), `K_HARB` 3 (one per island), `K_ROCK` 4 (plays as sea,
D30); `K_P1` (bit 7) marks player 1's squares.

**Grid ↔ screen** (`display.asm`): `MAP_IDX` (column, row → grid
index), `MAP_PUT` (draw a tile at column, row), `HPOS_COL` (P/M
horizontal position → column, `HP_MAP` = 48) and `PMY_ROW`
(double-line P/M line → row, `PM_MAP` = 24). A normal-width player
covers exactly one square.
